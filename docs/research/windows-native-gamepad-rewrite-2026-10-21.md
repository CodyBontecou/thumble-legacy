# Windows native gamepad feasibility for the TypeScript rewrite

Date: 2026-10-21. Research only; no driver selected, installed, or independently tested. Windows and optical live sync remain mandatory launch requirements. This note supports M0/M1 and does not certify the eight phone/receiver/game combinations. The later [headless execution decision](../rewrite-evidence/m0/headless-execution-decision.md) permits M2 engineering while physical beta/release acceptance remains pending.

## Decision

Investigate **HIDMaestro's Xbox 360 UMDF2/XUSB path** first in an isolated Windows M1 trial, with the read-only native XInput consumer probe. Its MIT license and local operation make it a stronger initial fit than libvirtualhid's licensed driver package. This is a recommendation for evaluation, **not adoption**. Its documented certificate flow locally trusts a self-signed certificate; that does not establish a normal signed Thumble release path, Secure Boot/HVCI compatibility, or WoW recognition. None of those gates was demonstrated by this research.

Do not implement a new KMDF driver speculatively and do not select retired ViGEmBus by default. Keep receiver platform selection behind the existing native-output boundary. TypeScript/Bun remains configuration authority; native input stays outside the JavaScript sample loop. Live sync needs its separate Windows capture/helper acceptance and cannot be certified by an XInput probe.

### libvirtualhid licensing and offline operation

The C++ library is MIT, but its [license map](https://github.com/LizardByte/libvirtualhid/blob/1aea6e37040205ad11cb8633f31ff876b5d7498d/LICENSES/license-map.md) assigns Windows driver/broker/package artifacts to [LB-SAL 1.0](https://github.com/LizardByte/libvirtualhid/blob/1aea6e37040205ad11cb8633f31ff876b5d7498d/LICENSES/LicenseRef-LizardByte-SAL-1.0.md). That text reserves redistribution and commercial use without additional permission. Do not bundle the driver under the library's MIT license or equate buying an end-user activation with redistribution rights. Written commercial/distribution terms would be needed before choosing it for a Thumble package.

Its pinned [Windows documentation](https://github.com/LizardByte/libvirtualhid/blob/1aea6e37040205ad11cb8633f31ff876b5d7498d/docs/windows-driver.md) describes a production-signed MSI for Windows 11 21H2+ AMD64, best-effort Windows 10 2004+, and no ARM64 release package. It requires a machine license. Yearly activation needs online validation after reboot and within 25 hours; an already activated lifetime license has a one-device offline allowance. These behaviors conflict with assuming an unconditional account-free/offline receiver. “Production-signed” here is upstream documentation, not independent verification of a downloaded MSI.

## HID is not XInput acceptance

Microsoft's [XINPUT_GAMEPAD](https://learn.microsoft.com/en-us/windows/win32/api/xinput/ns-xinput-xinput_gamepad) has separate 0–255 left/right trigger fields. Microsoft's [DirectInput/XUSB mapping](https://learn.microsoft.com/en-us/windows/win32/xinput/directinput-and-xusb-devices) combines LT and RT on the Z axis, losing some simultaneous combinations. Therefore `joy.cpl`, a generic HID enumerator, browser testing or a green stick display cannot alone prove Thumble's LT/RT/LT+RT banks. A custom HID descriptor may expose independent values, but actual consumer behavior is the acceptance target.

Read both triggers with native `XInputGetState` while submitting (0,0), (255,0), (0,255), (255,255), then partial asymmetric values. Verify sticks/buttons and that one logical controller appears. Repeat in the **exact WoW Classic Era + ConsolePort** and **Forever native gamepad** clients, with Steam Input state recorded. Each game's own interface must distinguish banks and release correctly. Upstream HIDMaestro [internals](https://github.com/hifihedgehog/HIDMaestro/blob/5f73b6fd64f00b2cba5ae5aba848645061029551/docs/INTERNALS.md) describe distinct HID/DirectInput/XUSB paths; treat those as implementation claims pending this test.

## Signing, security and lifecycle

Microsoft's [VHF guide](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/virtual-hid-framework--vhf-) documents its supported HID-source implementation as kernel mode (KMDF/WDM); it does not promise virtual Xbox/XInput compatibility. A first-party VHF/KMDF implementation would add driver ownership, deployment and maintenance. Microsoft's [current kernel signing policy](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/kernel-mode-code-signing-policy--windows-vista-and-later-) requires new kernel drivers to be Dev Portal signed on modern Windows, with production HLK/HCK submission guidance. Do not apply legacy cross-signing exceptions as the launch design.

UMDF avoids owning a kernel-mode binary, but still requires an installable trusted driver package. Microsoft's [signing tutorial](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/windows-driver-signing-tutorial) distinguishes user-mode signing and installation requirements. HIDMaestro's locally added Root/TrustedPublisher certificate is a machine trust-store mutation; a successful developer run is insufficient release evidence. Require a documented trusted-publisher packaging route, exact artifact signature verification, clean-machine installation with Secure Boot and memory integrity enabled, and no disabled security policy. Microsoft's [HVCI guidance](https://learn.microsoft.com/en-us/windows-hardware/test/hlk/testref/driver-compatibility-with-device-guard) explicitly calls for functional testing with memory integrity enabled; relevant kernel components require its verifier/HLK checks too.

HIDMaestro provides [uninstall documentation](https://github.com/hifihedgehog/HIDMaestro/blob/5f73b6fd64f00b2cba5ae5aba848645061029551/docs/UNINSTALL.md) and a preview-capable remover. Test shared-driver ownership and coexistence rather than deleting another application's package or certificate. Microsoft distinguishes [devnode removal from driver-store removal](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/how-devices-and-driver-packages-are-uninstalled); uninstall acceptance must inspect both and survive reboot. Retain before/after inventories, installer logs, published INF names, certificate thumbprints and residual-device checks.

## Next bounded M1 work and missing evidence

1. Pin the actual Windows machine, architecture, OS/build, game builds and ConsolePort hash. None is available in this research; AMD64 is a proposed first trial, not a narrowed launch promise.
2. Produce a candidate artifact manifest (commit, version, hashes, signatures, license notices, installed files/services/certificates). Establish production trust/distribution path before adoption. Use an isolated clean Windows machine for the trial.
3. Run independent native XInput trigger/readback, both game recognition tests, physical iOS/Android transport latency, cancellation, lost-release repair, crash/disconnect neutralization, suspend/reconnect and receiver restart. Cross-compiling is not installed-device proof.
4. Test upgrade/rollback/uninstall/reinstall, reboot, coexistence with physical controllers and other virtual-driver users, least-privilege steady state, Secure Boot/HVCI, and required Windows optical live sync.
5. Attach exact logs/artifacts to the M1 gate. No candidate currently satisfies these Thumble gates from inspected evidence; keep physical/release acceptance pending while implementation proceeds under the approved headless policy.
