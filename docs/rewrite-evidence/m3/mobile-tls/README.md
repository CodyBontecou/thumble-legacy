# M3 native phone TLS libraries

Both native platforms now exchange control frames and sealed input packets with the isolated Rust recording receiver over real TLS. This adds transport libraries and headless interoperability witnesses; it does not enable a product listener, authenticate a phone or complete M3.

The Swift Network.framework client enforces TLS 1.3, fixed ALPN/name, exact leaf pinning and Security.framework name/time/server-usage checks. It owns bounded native send state: one frame in flight, eight queued controls and one replaceable latest sealed input. Actual loopback tests verify coalescing, no input backlog, terminal control overflow, cancellation/close behavior, replay rejection and invalid certificate policy. Its main-actor API is native and independent of JavaScript; Network.framework owns socket I/O.

The Kotlin platform SSLSocket adapter is immutable/thread-confined at the frame/connection boundary and runs blocking operations under a deadline watchdog. It verifies the exact pin plus standard name/time policy and explicitly checks server-auth usage. A fresh SSLContext and TLS 1.3-only configuration prevent session resumption/downgrade. This is a low-level network-worker interface, not a nonblocking input callback. Native worker integration must precede production sampling. Android API 26 input support remains; the platform TLS adapter requires TLS 1.3/ALPN support from API 29+. The launch OS matrix is still an M0 decision, and older providers fail closed.

Local verification passes **19 Swift tests**, **33 Android JUnit tests with zero skips**, Android AAR/lint, both iOS SDK 26.5 static-module builds targeting iOS 17, Rust Clippy and the independent Node/OpenSSL witness. The real TLS tests used the freshly built native probe through `THUMBLE_NATIVE_TLS_PROBE`; unconfigured test runs explicitly skip those socket checks. The future mobile CI workflow builds/configures that probe. JVM checks use JDK 17, so actual Android provider/physical-device evidence remains pending.

Two live regressions were found and fixed. The Swift C verification callback inherited MainActor and asserted when Network.framework invoked it on the network queue; declaring the callback `@Sendable` fixes the executor boundary. The JVM provider accepted a client-only pinned leaf installed as a trust anchor; explicit extended-key-usage validation closes that bypass. Real handshake tests reject wrong pins and pinned certificates with expired/future validity, wrong names and client-only usage on both platforms. Test keys/certificates are synthetic and never represent production trust.
