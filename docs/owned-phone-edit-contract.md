# Owned phone layout intent v1

The `OwnedPhoneEdit` codec and private staging backend now connect to the headless receiver through authenticated `owned_phone_edit` / `owned_phone_edit_result` messages. Explicit owned authorities accept these requests only from a currently authenticated peer that negotiated format 5. Shipping phone offers remain `[4]`; mobile journals and automatic migration are not activated. Legacy pending edits remain untouched.

An intent contains a schema version, globally unique edit UUID, profile UUID, exact base configuration revision, per-control changes, removed control UUIDs, and an optional system/light/dark preference. Changes cover normalized center coordinates, scale, rotation, visibility, location lock and stacking order. It accepts no full customization, appearance bank, output/binding change, package reference, path, profile selection, or orientation variant. Unknown fields and duplicate JSON keys fail closed. UUID strings must use canonical hyphenated form, with either letter case. Nil UUIDs, duplicate owners, overlapping changed/removed controls, empty intents, nonfinite/out-of-range geometry and oversized requests are rejected.

The request ceiling is 64 KiB and the combined number of changed/removed controls is 128. Scalar limits match the retained native operations. The JSON Schema documents structural constraints; the typed validator additionally enforces cross-collection uniqueness/counts. The host validates that every requested control belongs to the named canonical landscape profile before creating private storage.

Staging requires an exact owned authority snapshot at the supplied revision. Draft, intent-marker, operation and commit IDs derive from the edit UUID. A no-op marker binds the complete intent digest before any native work, so altering a later operation cannot reuse an already-prepared prefix. Each operation then uses the existing durable draft log. A native failure leaves authority bytes unchanged; retry resumes only unfinished operations. A matching committed receipt returns its original result without applying again. Reusing an edit UUID with different content is refused. Replay remains subject to the existing bounded commit history.

Native operations preserve canonical outputs and other executable declarations, raw future metadata, resource tables and all saved paint states. Custom deletion removes the corresponding paint owner from each state and reconciles its binding ownership; preset deletion uses the existing hide behavior. Geometry and color preference never replace saved appearance with transient rendered paint.

The staging API itself does not authenticate or install authority bytes. The receiver validates the negotiated peer and queues bounded reliable jobs. Native staging and commit preparation run outside the input mutex. At commit it rechecks the same registered, authenticated format-5 connection, applies the normal held-input release barrier and revision/CAS persistence, then returns a result correlated to the exact edit/profile IDs. Paired-phone authorization is separate from the local agent `--allow-config-write` flag; local agent writes remain disabled without that opt-in. Revocation, queue backpressure, invalid/mixed payloads and release failures cannot commit.

Owned pairing/profile snapshots publish `configurationRevision` and `owned_phone_edit_v1`. Legacy snapshots are unchanged. Requests require `profileFormatVersion: 5` and the `ownedPhoneEdit` object. Results contain `schemaVersion`, `editID`, `profileID`, `baseConfigurationRevision`, current `configurationRevision`, `changed`, and `status` (`applied`, `replayed`, `conflict`, or `rejected`). Successful results also contain historical `committedRevision`; failures contain a bounded static `errorCode`. A replay may report committed revision 42 with current revision 43. It must not roll back a newer snapshot. Replays use durable receipts and do not require the native helper. New fields always use JSON rather than disappearing into compact input frames; misplaced edit payloads cannot execute button input.

Phone journals must retain failed/conflicting edits for recovery and clear only the matching acknowledged intent. Snapshot receipt alone is insufficient. Remaining work is iOS/Android journal adapters with snapshot/ack reconciliation, migration of pending legacy edits against original orientation, full transfer bounds/fidelity and retained-peer acceptance, then profile-format/migration activation.

`Host/fixtures/owned-phone-wire/v1` freezes request and applied/replayed/conflict/rejected frames, including historical-versus-current revisions. `scripts/verify-owned-phone-wire.py` runs an actual temporary receiver with local agent writes disabled, verifies authenticated editing, refusal/replay behavior, all eight paint states and exact metadata, and retries across receiver restart. It requires explicit host/native-helper paths and never uses an existing user's authority.

`Host/fixtures/owned-phone-edits/v1` freezes a valid native-verifiable intent, malformed/safe contract cases and schema hashes. The developer example `verify_owned_phone_edit` runs real native geometry/deletion/preference operations against a private fixture authority, checks paint/resources/declarations/bindings, stages a retry and prepares a commit/replay. Production receiver integration must use its normal authenticated release/CAS path; the example has no live input owner.
