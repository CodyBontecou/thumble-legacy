# Owned phone layout intent v1

The `OwnedPhoneEdit` codec and private staging backend now connect to the headless receiver through authenticated `owned_phone_edit` / `owned_phone_edit_result` messages. Explicit owned authorities accept these requests only from a currently authenticated peer that negotiated format 5. Normal Android and iOS startup now admits `[4, 5]` only after all legacy journals load successfully and are empty. Otherwise the offer stays `[4]`, preserving pending edits for reconciliation with their legacy owner. The generic legacy DTO/stored-format policy remains `[4]`; dedicated owned readers handle format 5. Automatic startup migration remains disabled.

An intent contains a schema version, globally unique edit UUID, profile UUID, exact base configuration revision, per-control changes, removed control UUIDs, and an optional system/light/dark preference. Changes cover normalized center coordinates, scale, rotation, visibility, location lock and stacking order. It accepts no full customization, appearance bank, output/binding change, package reference, path, profile selection, or orientation variant. Unknown fields and duplicate JSON keys fail closed. UUID strings must use canonical hyphenated form, with either letter case. Nil UUIDs, duplicate owners, overlapping changed/removed controls, empty intents, nonfinite/out-of-range geometry and oversized requests are rejected.

The request ceiling is 64 KiB and the combined number of changed/removed controls is 128. Scalar limits match the retained native operations. The JSON Schema documents structural constraints; the typed validator additionally enforces cross-collection uniqueness/counts. The host validates that every requested control belongs to the named canonical landscape profile before creating private storage.

Staging requires an exact owned authority snapshot at the supplied revision. Draft, intent-marker, operation and commit IDs derive from the edit UUID. A no-op marker binds the complete intent digest before any native work, so altering a later operation cannot reuse an already-prepared prefix. Each operation then uses the existing durable draft log. A native failure leaves authority bytes unchanged; retry resumes only unfinished operations. A matching committed receipt returns its original result without applying again. Reusing an edit UUID with different content is refused. Replay remains subject to the existing bounded commit history.

Native operations preserve canonical outputs and other executable declarations, raw future metadata, resource tables and all saved paint states. Custom deletion removes the corresponding paint owner from each state and reconciles its binding ownership; preset deletion uses the existing hide behavior. Geometry and color preference never replace saved appearance with transient rendered paint.

The staging API itself does not authenticate or install authority bytes. The receiver validates the negotiated peer and queues bounded reliable jobs. Native staging and commit preparation run outside the input mutex. At commit it rechecks the same registered, authenticated format-5 connection, applies the normal held-input release barrier and revision/CAS persistence, then returns a result correlated to the exact edit/profile IDs. Paired-phone authorization is separate from the local agent `--allow-config-write` flag; local agent writes remain disabled without that opt-in. Revocation, queue backpressure, invalid/mixed payloads and release failures cannot commit.

Owned pairing/profile snapshots publish `configurationRevision` and `owned_phone_edit_v1`. Legacy snapshots are unchanged. Requests require `profileFormatVersion: 5` and the `ownedPhoneEdit` object. Results contain `schemaVersion`, `editID`, `profileID`, `baseConfigurationRevision`, current `configurationRevision`, `changed`, and `status` (`applied`, `replayed`, `conflict`, or `rejected`). Successful results also contain historical `committedRevision`; failures contain a bounded static `errorCode`. A replay may report committed revision 42 with current revision 43. It must not roll back a newer snapshot. Replays use durable receipts and do not require the native helper. New fields always use JSON rather than disappearing into compact input frames; misplaced edit payloads cannot execute button input.

Phone journals must retain failed/conflicting edits for recovery and clear only the matching acknowledged intent. Snapshot receipt alone is insufficient. Both retained mobile transports now have snapshot/ack reconciliation and conflict retry paths in normal guarded startup. The actual Pixel client has drained a legacy layout journal, reconnected to prove owned admission, survived an explicit receiver migration with the same trust, and committed a new owned edit. Missing/unsupported legacy recovery data, edits made during cutover, automatic authority migration, and live WoW capture/input and game-driven character-switch acceptance remain separate requirements.

`Host/fixtures/owned-phone-wire/v1` freezes request and applied/replayed/conflict/rejected frames, including historical-versus-current revisions. `scripts/verify-owned-phone-wire.py` runs an actual temporary receiver with local agent writes disabled, verifies authenticated editing, refusal/replay behavior, all eight paint states and exact metadata, and retries across receiver restart. It requires explicit host/native-helper paths and never uses an existing user's authority.

`Host/fixtures/owned-phone-edits/v1` freezes a valid native-verifiable intent, malformed/safe contract cases and schema hashes. The developer example `verify_owned_phone_edit` runs real native geometry/deletion/preference operations against a private fixture authority, checks paint/resources/declarations/bindings, stages a retry and prepares a commit/replay. Production receiver integration must use its normal authenticated release/CAS path; the example has no live input owner.

## Apple wire and journal adapter

`Sources/Shared/OwnedPhoneEdit.swift` reads the frozen scalar intent/result contract. Canonical nonnil UUIDs, unsigned 64-bit revisions, integer token kinds, unknown fields, duplicate keys, scalar limits and ownership uniqueness are checked. The public wire codec preserves JSON for new fields and rejects misplaced or mixed edit payloads. Legacy compact fixtures are unchanged. Strict snapshot revision checks apply to the header rather than opaque nested metadata.

`OwnedPhoneEditJournal` keeps exact intent and owned recovery-document bytes. Its private version-1 storage deduplicates recovery data by SHA-256, validates document/profile ownership, bounds records and total bytes, preserves first-per-profile upload order and refuses changed requests with reused IDs. Atomic saves are gated by validation of an existing file; corrupt recovery data cannot be overwritten by an empty journal. iOS writes use file protection until first unlock.

Journal acknowledgment requires the same authenticated authority, negotiated format 5, a matching edit/profile/base revision and a successful explicit receipt. Conflicts/rejections and ordinary snapshots retain pending edits. The reducer changes only the journal, so a historical receipt cannot replace a newer snapshot. Transport callers must retain current connection identity and publish journal changes only after persistence succeeds.

`OwnedPhoneSnapshot` extracts canonical profile-array bytes with the existing duplicate-key scanner, retains the received tokens, validates the owned document, and prepares native display profiles separately. Pairing credentials remain connection metadata and never enter the owned cache. `OwnedPhoneCache` atomically stores the source, journal and local selection/default preferences. Its 24 MiB disk ceiling accommodates two independently bounded 8 MiB records plus base64 overhead; network and journal bounds remain unchanged. Corrupt files and unknown cache fields block saves rather than resetting data.

`OwnedPhoneLayoutAdapter` derives geometry/hide/delete/preference intents and proves that applying them reproduces the editor change. Paint, resources, labels, outputs, added controls and portrait variants cannot be smuggled into that channel. `OwnedPhoneSession` builds optimistic display profiles while retaining original source and recovery bytes. It defers an early successful receipt until the corresponding snapshot is available. An explicit conflict plus an advancing snapshot permits a new edit UUID/revision; original uncertain request bytes never change. Missing controls remain pending for review and cannot be recreated implicitly.

The iOS `ControllerClient` uses these transactions before publishing or sending. Gesture previews are ephemeral; completed edits enter the journal before reliable upload. Snapshots do not acknowledge entries, revocation leaves the cache intact, and character changes invalidate the editor's original profile identity. Local offline selection/default preferences are cached separately from authority source and reset on the next full server snapshot. Existing legacy pending layouts are neither converted nor cleared; corrupt legacy skin journals now fail startup before writes. Generic `ProfileFormatPolicy.supportedFormats` remains `[4]`; normal app startup uses the dedicated `[4, 5]` admission path only when every legacy journal is empty.

`Tests/iOS/OwnedPhoneClientTests.swift` runs the actual client in a dedicated hosted XCTest target. It verifies explicit acknowledgments, conflict replay, early-receipt deferral, A/B/A selection, stale-editor cancellation, legacy admission and Mac-scoped pending edits. The app shell's automatic reconnect is disabled during these tests; the test clients use disposable caches and restore simulator preferences. `scripts/verify-owned-phone-ios.py` runs its real-receiver case against a temporary `--no-input` authority and native helper. Android has equivalent isolated Pixel persistence/mock-peer tests and `scripts/verify-owned-phone-android.py`. Both real-client harnesses verify committed geometry/preference edits, correlated receipts, confirmed A/B/A selection and exact unrelated Mac source preservation. These are transport checks rather than live-game or physical-input acceptance.


## Legacy drain and migration admission

The receiver CLI/MCP status now reports `core.clientSupportsOwnedProfiles` only for the authenticated active peer that offered format 5 at its current handshake. For the retained clients, this is evidence that their legacy layout/appearance/selection/removal journals loaded and were empty at that handshake. It is not a claim about disconnected phones or edits made afterward. Android now includes pending/corrupt skin removals in this guard, matching iOS.

Before migration, connect the phone to the legacy authority, let supported journals commit and receive their normal acknowledgments, then reconnect. Check the authenticated format-5 offer before stopping the specific receiver and applying its exact migration plan. A peer with pending legacy work refuses owned snapshots and retains its saved data; never clear its journals or alter format markers to admit it. Incomplete recovery, missing owners or unavailable original packages require review rather than automatic conversion from a display projection.

`scripts/verify-phone-authority-migration.py` exercises this actual Pixel-client sequence using disposable phone storage and a real no-input receiver/native helper. A queued format-4 landscape edit commits at revision 42, the phone's journal drains durably, a fresh handshake offers format 5, the exact backed-up migration advances to 43, and the same credential reconnects and commits an owned color preference at 44. Installed receiver state and real phone storage are untouched.

This test exposed a native legacy replacement bug: a new orientation slot lost submitted layout extension fields while the primary layout retained them. `ThumblePhoneLayoutBridge` now applies native normalization/dehydration to the submitted raw layout and preserves its extensions in both the primary and target orientation slots. The native oracle test verifies preservation and no-op replay. Full stack checks retain the existing budgets.


Admission is rechecked when each format-5 frame arrives, before changing credentials, caches, profiles or capability state. A clean hello is not enough: if an offline legacy edit is recorded while the handshake is in flight, both clients close the connection with reconciliation guidance and retain the legacy cache and journal. Hosted iOS and actual Pixel regressions exercise this timing explicitly. Removing an unused local archive while showing an owned profile creates no new legacy removal intent on either phone.

For an unchanged migration destination, the agent can use the original plan with the stopped receiver's [exact-plan rollback](authority-migration.md), reconcile supported pending work with its legacy owner, and prepare a new migration. Newer receiver state or conflicting installed archives block rollback rather than being overwritten. Phones with missing owners or work that cannot be reconciled still require explicit recovery review; neither a successful fixture test nor a format offer establishes that every real phone journal is ready.
